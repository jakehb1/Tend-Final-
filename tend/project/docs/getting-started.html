Getting started.

From zero to a live agent reading your ontology in under 30 minutes. This guide assumes a fresh workspace, a warehouse you can read from, and one source system to write back to.

Prerequisites

  • Python ≥3.11 or Node ≥20.10
  • A workspace token — request via tend login or the admin console
  • Warehouse read credentials (Snowflake, BigQuery, Databricks, or Redshift)
  • At least one source system with write credentials (Salesforce, HubSpot, Pipedrive, Shopify, Kajabi, Stripe — full list in Connectors)

Install the CLI

shellpip install tend-sdk
tend --version
# → tend 1.4.2 (runtime 2026.04)

The SDK bundles the CLI, the Python client library, and local validators (schema linting, policy simulation, agent replay). Expect ~180MB installed.

Bootstrap a workspace

The tend init command introspects your warehouse, detects candidate entity types, and emits a first-pass schema to schema/. Review it before pushing — the planner makes conservative guesses that usually need one round of cleanup.

shelltend init \
  --from-warehouse snowflake://acme/prod.analytics \
  --detect-entities \
  --out ./schema

# Detected: Account(2.1M rows) · Contact(8.4M) · Deal(412k)
# Wrote schema/account.tend, contact.tend, deal.tend

Your first schema

Open schema/account.tend. The DSL is declarative. Every entity has an id type, typed fields, zero or more relations, and optional computed facts.

schema/account.tendentity Account {
  // identity & surrogate key
  id: uuid primary
  external: {
    salesforce_id: string unique
    hubspot_id:    string? unique
  }

  // core fields
  name:   string
  tier:   enum("smb", "mid", "ent")
  region: enum("us", "eu", "apac")
  arr:    money

  // relations
  owned_by: Contact via "primary_owner"
  deals:    collection<Deal>

  // derived fact — recomputes on any upstream write
  health: computed {
    risk_score() < 0.3 ? "green"
      : risk_score() < 0.6 ? "yellow"
      : "red"
  }
}

Push & deploy

shell# validate locally
tend lint
# ✔ 14 entities, 38 relations, 6 computed facts, 0 warnings

# dry-run the migration plan
tend plan --target staging
# + Account.health : computed (new)
# ~ Deal.stage    : enum → enum (values: +"evaluation")
# - Lead          : entity (deprecated, 14d grace)

tend deploy --target staging
Migrations are versioned
Every deploy produces a signed migration artifact stored in your workspace bucket. Rollback is tend rollback --to v17. Nothing is destructive by default — deprecated entities linger for 14 days.

Wire up your first agent

Agents are typed functions. They declare what they can read, what they can write, and what tools they can call. The runtime enforces every boundary at execution time — an agent cannot exfiltrate fields it didn't declare.

agents/renewal_risk.pyfrom tend import agent, ontology as o

@agent(
    name="renewal-risk-v3",
    reads=[o.Account, o.Deal, o.Contact],
    writes=[o.Account.health_note],
    tools=["slack.post_to_channel"],
    model="claude-sonnet-4.5",
)
def run(account: o.Account) -> None:
    ctx = account.typed_context(depth=2)
    verdict = reason(
        "Does this account show renewal risk?",
        context=ctx,
    )
    if verdict.risk > 0.6:
        account.health_note = verdict.explanation
        tools.slack.post_to_channel(
            channel="#csm-alerts",
            text=f"{account.name}: {verdict.explanation}",
        )

Deploy it and bind a trigger. The agent will run on every change to Account or its related Deal and Contact entities.

shelltend agent push ./agents/renewal_risk.py
tend trigger bind \
  --agent renewal-risk-v3 \
  --on "Account.* OR Deal[account].* OR Contact[account].*" \
  --rate-limit "120/min, $50/day"

Verify in production

Every agent run is observable. Tail the run log with the CLI or open the console's run explorer.

shelltend runs tail --agent renewal-risk-v3
# 2026-04-19T21:14:02Z run_8f2c ok    · acct:4102 · 1.4s · 2,140tok · $0.018
# 2026-04-19T21:14:05Z run_8f2d ok    · acct:9201 · 1.1s · 1,870tok · $0.015
# 2026-04-19T21:14:09Z run_8f2e block · acct:7744 · policy/eu-pii-read
Policy blocks are not errors
A block verdict means the runtime refused the agent's read or write because a policy denied it. The agent's reasoning is preserved in the run record. Either relax the policy or narrow the agent's declared surface — never both at once.
