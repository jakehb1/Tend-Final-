The mental model.

Four primitives. A temporal commit log. A policy gauntlet around every read and write. If you internalize these three ideas, every other concept in tend falls into place without memorization.

The four primitives

Everything in tend is one of four kinds. Pick the right kind for the fact you're modeling and most downstream decisions (indexing, lineage, replay) are made for you.

PrimitiveHas identity?Mutable?Use when
entityyes, stableversionedA noun your team argues about: Account, Deal, Invoice.
relationyes, typed edgeversionedA connection with its own lifecycle: Subscription, Membership.
eventopaqueneverA thing that happened: PageView, PaymentFailed.

The entity vs event heuristic

The single most common modeling mistake is reaching for an entity when you want an event (or vice versa). Ask: if this record's values change, do I want the old values preserved as history, or replaced?

  • Replaced → entity. You want Account.tier to reflect the current tier, with history on request.
  • Preserved → event. You want every TierChanged to live forever as its own row.

You often want both. Model the entity, emit the event, let the ontology link them.

Temporal is not optional

Every write produces a new version. Every read is implicitly as of now, but can be explicitly as of then. This is what makes agents safe to deploy: they can reason against the exact state of the world that caused an event, not whatever the state happened to be when the agent got scheduled.

acct = Account.get(ticket.account_id, at=ticket.created_at)

Policy is part of the model

Policy is not a layer on top of the data. It's part of the type system. A field with a pii tag is structurally distinct from an untagged field; the compiler refuses to let an agent read it without the pii:read capability.

Consequence
You cannot accidentally exfiltrate a field. The runtime will refuse, and the refusal is a typed exception your workflow can catch. Not a silent omission from the response.

How a change propagates

When a write lands, five things happen in order. Each stage is observable and replayable.

  1. Admit. The write is validated against the schema and policy.
  2. Commit. A new version is appended with lineage metadata.
  3. Invalidate. Dependent computed fields are marked stale.
  4. Notify. Any agent or workflow bound to the entity's change stream is enqueued.
  5. Emit. Webhooks, downstream syncs, and audit records are dispatched.

Anti-patterns

Modeling a JSON blob

If you find yourself writing payload: json, stop. Either model the fields, or use an event. Blob-typed fields undermine every downstream capability (resolution, policy, lineage, query).

Using an entity for a log

If records are append-only and never mutated after creation, they're events. Entities carry the overhead of versioning, resolution, and lifecycle. Wasted on logs.

Bypassing computed fields

When two agents compute health the same way, extract a computed field. You will never convince both agents to stay in sync on their own.
