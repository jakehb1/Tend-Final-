The ontology.

The ontology is a typed, temporal, versioned graph of your business. Every fact has a type, a source, and a timestamp. The DSL compiles to a storage-agnostic IR the runtime executes over a columnar-plus-graph engine.

The object model

Four primitive kinds, composed into arbitrary graphs:

KindPurposeMutability
entityA typed object with stable identityversioned, append-only history
relationA typed edge between two entitiesversioned, first-class lifecycle
eventAn immutable fact, timestampedappend-only
computedA derived fact, recomputed on dep writeslazy, cached, invalidated by lineage

The DSL

Schema lives in .tend files, checked into your repo. The grammar is small, strict, and diffable. A full reference is available under Grammar.

schema/deal.tendentity Deal {
  id:      uuid primary
  account: Account required
  owner:   User
  amount:  money
  stage:   enum("lead", "qual", "evaluation", "closed_won", "closed_lost")
  closed_at: timestamp?

  // lifecycle. Declarative state machine
  lifecycle {
    lead      → qual       requires owner
    qual      → evaluation requires amount > 0
    any       → closed_*  sets closed_at = now()
  }

  // derived
  age_days: computed { days_between(now(), created_at) }
  is_stale: computed { age_days > 45 and stage in ["lead", "qual"] }
}

Temporal semantics

Every write to the ontology is append-only. The storage engine maintains three time axes per entity:

  • observed_at. When tend ingested the fact
  • effective_at. When the fact was true in the world
  • tx_at. The monotonic transaction timestamp for causal ordering

This lets you ask questions like "what did we believe about Account 4102 at 09:00 last Tuesday?" in a single query. Temporal reads are first-class:

queryfrom o import Account

# point-in-time read
acct = Account.get("acct_4102", at="2026-04-15T09:00:00Z")

# changelog. Every state transition
history = acct.history(fields=["tier", "arr"])

Schema versioning

Every tend deploy produces a signed, numbered schema version. Migrations are planned statically: the compiler refuses deploys it cannot prove safe without an explicit migration block.

Safe-by-default operations
Additive changes (new field, new entity, new relation) auto-migrate. Breaking changes (drop field, rename, tighten enum) require an explicit migrate{} block with forward + back transforms. 
migrations/v18.tendmigrate v17 → v18 {
  rename Account.plan → Account.tier
  backfill Account.health from "computed"
  assert count(Account) == count_before(Account)
}
